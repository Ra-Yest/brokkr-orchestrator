### Этап 1. `v0.4.x` — Боевая обкатка и сжатие контекста
*Гейт старта: сначала прогнать `v0.4.0` на чистом `gungnir-vpn v2`, сравнить `orchestrator stats` со старыми `wasted=60.84%` / `escape_rate=40%` и закрыть оставшиеся точечные боли.*

- **Attempt Compaction & `handoff.json`:** компактная выжимка после каждой задачи и между неудачными попытками (`decisions`, `assumptions`, `what_failed_before`, лимит ~10 строк), чтобы на 2–3 круге воркер не читал простыню старых логов.
- **Умный срез интерфейсов (`surface_extract_cmd`):** опциональная команда проекта в `pipeline.yaml`, вытаскивающая только публичные сигнатуры/типы для `Seam Capsule` и `REPO_MAP.md` (ядро остаётся stack-agnostic, без встраивания tree-sitter).
- **Локальный `fix_seam` + DAG Circuit Breaker:** при `CRITICAL` от `seam_auditor` — опционально замораживать зависимую ветку и порождать 1–2 попытки локальной починки стыка с чистой остановкой ветки при провале.
- **Чистка `cli.py` (по необходимости):** при росте команд разбить `cli.py` (~1070 строк) по подкомандам.

### Этап 2. `v0.5.0` — Mission Control UI (тонкий слой поверх состояния)
*Строгий инвариант: UI полностью отвязан от раннера (читает `events.jsonl`, `state.json`, `tasks.json`, `.pipeline/seam_audits/` и пишет команды в `control_inbox/`), поэтому любой баг UI никогда не уронит прогон.*

- **Backend (`orchestrator ui`):** лёгкий FastAPI-сервер с SSE/WebSocket-стримом новых строк `events.jsonl` + REST-эндпоинты для записи в `control_inbox/` (мягкая пауза, resume, перезапуск failed-задачи, вброс заметки/правки).
- **Frontend (React/Vite, локально или через Tailscale / Cloudflare Tunnel):**
  1. Живая доска и DAG-граф: статусы задач, активный провайдер/аккаунт, заблокированные по `depends_on` ветки, индикатор `BATCH_PENDING` / `NEEDS_REVIEW`.
  2. Пульт AFK: мягкая пауза, стоп, рестарт задачи в 1 клик, поле быстрого ввода в `control_inbox`.
  3. Инспектор артефактов: очищенный `git diff`, логи гейтов, результаты Evidence-Bound Review, отчёты Seam Audit, карточки `NEEDS_ARCH_CHANGE`, скриншоты Playwright.
  4. Панель квот и телеметрии: таймеры 5-часовых окон и cooldown по провайдерам/аккаунтам + живые метрики из `stats.py` (`wasted_pct`, `escape_rate`).
- **Опциональный быстрый шаг (`v0.4.5`):** консольный TUI на Python (Textual) как живой монитор в терминале до веб-дашборда.
- *Бонус:* сам веб-дашборд `v0.5.0` можно скормить оркестратору как отдельный боевой проект.

### Этап 3. `v0.6.0` — Командная ферма (План 2: 2–3 ПК через GitHub)
*Цель: сложение лимитов Antigravity нескольких участников через GitHub без своего сервера и БД (поверх `BaseTaskStore`).*

- **`GitHubTaskStore` (`stores/github_issues.py` через `gh` CLI):**
  - Задачи живут в GitHub Issues с лейблами (`todo`, `in-progress`, `needs-review`, `changes-requested`, `needs-arch-change`, `easy`/`medium`/`hard`, `pc-1`/`pc-2`).
  - Стандартизированный YAML-блок в шапке тела Issue (`depends_on`, `allowed_paths`, `context_files`, `provides`, `consumes`).
  - Защита от race condition при захвате: jitter (2–10 с) → комментарий `CLAIM: <pc_name>` → пауза 3–5 с → перечитывание треда; работает первый timestamp.
- **Режим `orchestrator worker` (ПК друзей):** берёт `changes-requested`, потом `todo`, работает в отдельной ветке; `PROGRESS.md`, `REPO_MAP.md` и жёлтая зона в `red_protected` (shared-правки только через `NEEDS_ARCH_CHANGE`); локальные гейты + `pre_reviewer` → PR.
- **Облачный CI-фильтр (GitHub Actions):** сборка, линтер и тесты на каждый PR; при красном CI воркер сам забирает обрезанный лог и чинит до вызова `master`.
- **Режим `orchestrator master` (главный ПК):** мониторит только зелёные PR и `needs-arch-change`; гоняет `reviewer` (Evidence-Bound Review) + Seam Audit → мержит в `main` и обновляет `PROGRESS.md`/`REPO_MAP.md`, обрабатывает `NEEDS_ARCH_CHANGE`, запускает рефакторинг каждые 5–7 PR и сбрасывает зависшие `in-progress` через 40–60 мин.
- **Онбординг друга за 5 минут:** клон репо → `gh auth login` → `.env` с `PC_NAME` → `orchestrator worker`.

### Что сознательно НЕ тащим в оркестратор
- **Ночная самопочинка `runner.py` силами LLM:** при внутренней ошибке оркестратора — только fail-fast + трейсбек в Telegram.
- **Свободный чат между агентами и самомодифицирующийся DAG на лету:** вместо этого — неизменяемый на прогон `tasks.json`, типизированные контракты и односторонний `handoff.json`.
- **Языковые парсеры в ядре:** никаких хардкодных AST/import-анализаторов под Go/Dart/TS внутри `src/orchestrator/` — только проектные команды в `pipeline.yaml`.

## Идеи (Backlog)

### 1. Активный `seam_auditor` (не просто «выражает обеспокоенность», а чинит стык) (реализуется вместе с пунктом 7) [`v0.4.x`]
Сейчас при `CRITICAL` аудитор только сохраняет отчёт и ставит прогон на паузу, а при 'WARNING' БУКВАЛЬНО ПРОСТО ВЫРАЖАЕТ ОБЕСПОКОЕННОСТЬ. Чтобы `seam_auditor` реально закрывал расхождения:
- **Строгий структурированный вердикт:** вместо свободного текста возвращать `severity` (`OK` / `WARNING` / `CRITICAL`), `owner` (`producer` | `consumer` | `both`), `broken_clause_ids`, `target_files` (список файлов, которые нужно поправить) и `fix_order` (конкретный приказ на правку + ожидаемый тест/проверка).
- **Реакция по уровням:**
  - `WARNING` → не тормозит прогон, автоматически пишется в `handoff.json` / заметку следующей зависимой задачи (или в очередь `refactorer`) с разблокировкой сломанных файлов для воркера.
  - `CRITICAL` → **DAG Circuit Breaker** замораживает *только* ветку, зависящую от сломанного контракта (независимые задачи продолжают идти), и автоматически порождает ограниченную задачу починки стыка (`fix_seam`, лимит 1–2 попытки, `allowed_paths` строго ограничены `target_files` из вердикта + тесты, `context_files` включают обе стороны стыка и фикстуру).
- **Обязательная перепроверка:** после `fix_seam` прогоняются гейты и повторный `seam_auditor` на том же контракте. Если `OK` — ветка размораживается и коммит фиксируется; если за лимит попыток не починилось — ветка остаётся замороженной, уходит карточка в Telegram (без срыва остальных веток).
- **Опционально (для тяжёлых контрактов):** при `owner == both` и задетой жёлтой зоне эскалировать напрямую в `architect` (по аналогии с `NEEDS_ARCH_CHANGE`), а не гонять обычного воркера.

### 2. Наблюдаемость промптов (Prompt Audit Trail → Prompt Inspector) [`v0.4.x` → `v0.5.0`]
- **`v0.4.x`:** перед отправкой в `stdin` провайдера сохранять точный отрендеренный промпт в `.pipeline/prompts/<task_id>/a<attempt>_r<round>_<role>_<provider>.md` (`save_prompts: true`, авторотация). В `events.jsonl` писать только `prompt_file`, `prompt_chars`, `prompt_sha256` и разбивку объёма по секциям (`role`, `seam_capsule`, `context_files`, `gate_summary`, `review_diff`). Добавить метрики размеров промптов по ролям в `orchestrator stats`.
- **`v0.5.0`:** вкладка **Prompt Inspector** в Mission Control UI — просмотр полного промпта любого шага, разбивка «что съело контекст» и diff промпта между попытками.

### 3. Связка автофоллбэка с анлокером [`v0.4.x`]
- Добавить опциональный хук `network_recovery_command` в `pipeline.yaml` (3-ступенчатая эскалация):
  1. Сетевой/региональный сбой (`403`/`502`/`503`/обрыв TLS) → запрос к анлокеру на смену узла/проверку маршрута.
  2. Если анлокер вернул `RECOVERED` → повтор **того же** провайдера без cooldown (экономия квот резервного аккаунта).
  3. Только если повтор снова упал или анлокер `UNAVAILABLE` → реальный cooldown и переход на `fallback_providers` / гибернацию.

### 4. Регламентированный первичный разворот репо (в 2 этапа) [`v0.4.x` → после `v0.5.0`]
- **Этап 4.1 (`v0.4.x`) — `orchestrator init --spec <path>`:** one-shot разворот репозитория строго по готовому диздоку (генерация `pipeline.yaml`, `.contracts/fixtures/**`, `tasks.json`, `AGENTS.md`, `REPO_MAP.md`, `PROGRESS.md` + автогейт `plan-check --llm`), без диалога и лишнего расхода CLI-квот.
- **Этап 4.2 (после `v0.5.0`, только в браузере):** Discovery-интервью «Программист ↔ Коммерс» (ИИ опрашивает заказчика простыми вопросами и «продаёт» скоуп v1) живёт строго в веб-чате, чтобы не жечь агентские CLI-квоты на болтовню. Итоговый диздок уходит через браузерное расширение напрямую в `orchestrator init --spec`.

### 5. Браузерное расширение + скилл для веб-чата [`v0.5.0`]
- Скилл в веб-чате форматирует команды управления в типизированный блок `orchestrator-cmd`.
- Браузерное расширение (Manifest V3) парсит эти блоки из DOM и отправляет в локальный FastAPI (`v0.5.0`, `control_inbox/` с локальным Bearer-токеном). Разрушающие команды (`stop`, `reset_task`, правки `tasks.json`) — строго по клику; read-only запросы статуса/диффа можно прокидывать обратно в поле ввода чата.

### 6. Изучить и перенять паттерны из `herdr`, `Hermes` (`hermes-cli-orchestrator`), `CAO` [`v0.4.x` → `v0.6.0`]
- **Без LLM в контуре (из `hermes-cli-orchestrator`):** ручная команда из Telegram/UI для принудительной смены провайдера/аккаунта и сброса cooldown, работающая даже когда все модели лежат.
- **Live-probe и staged health-check:** активная проверка «ожил ли аккаунт» для досрочного снятия cooldown после 5-часового окна + live-проверка провайдеров в `orchestrator doctor`.
- **Event-driven статус `blocked` и reconcile (из `herdr` / `CAO`):** явный детект состояния «агент ждёт подтверждения/ввода» вместо ожидания `idle_timeout` + сверка/чистка зависших процессов при рестарте.
- **Удалённые машины по SSH (из `herdr --machine`):** рассмотреть как альтернативу/дополнение к `GitHubTaskStore` в `v0.6.0`.

### 7. Оркестрируемый `Diagnostician → Micro-Executor` для `refactorer` и `seam_auditor` [`v0.4.x`]
Заменить монолитного `refactorer` (риск часового зависания и полного отката) и пассивного `seam_auditor` единым двухфазным конвейером поверх эфемерной очереди `maintenance_queue` в `state.json` (не мутируя основной DAG в `tasks.json`):
- **Фаза 1 (Read-Only Планировщик, умная модель):** `seam_auditor` и `refactor_planner` ничего не правят на диске и возвращают строгий JSON с массивом точечных `fix_orders` (до 3–5 штук: `target_files`, `instruction`, `expected_test`, `verify_cmd`).
- **Фаза 2 (Исполнитель, быстрая модель на `flash`):** каждый `FixOrder` выполняется изолированно с `allowed_paths = target_files + tests`, коротким таймаутом (10–15 мин), гейтами и отдельным атомарным коммитом (провал одного приказа не откатывает остальные). `WARNING` от `seam_auditor` копятся до ближайшего чекпоинта `refactor_planner`; `CRITICAL` сразу ставит приказ в очередь и морозит только зависимую ветку.

### 8. Переосмысление Diff Guard и спасение артефактов после `stall` [`v0.4.x`]
- **Diff Guard — строгий по путям, мягкий по строкам:** оставить жёсткий блок только на `allowed_paths` / `red_protected` / замороженные фикстуры. Объём диффа перевести в `soft_warning` для ревьюера + высокий аварийный потолок (`anomaly_cap` ~10 000 строк) вместо жёстких порогов 1000/2500.
- **Спасение работы при `stall_detected` на выходе:** если агент завис на фоновом процессе уже *после* `provider_response_started` и изменил файлы на диске — прогнать Diff Guard и гейты по текущему дереву и при зелёном результате передать в ревью, не теряя работу.
- **Прозрачная телеметрия и профилактика:** логировать `reason=stall_bg_task` отдельно от `timed_out=True` и добавить в базовый системный промпт воркеров запрет на фоновые команды/subtasks.

### 9. Операционные команды раннера без ручного редактирования JSON/YAML [`v0.4.x`]
- **Hot-reload `pipeline.yaml` при `resume` (и команда `reload_config` в `control_inbox`):** перечитывать лимиты, таймауты и список гейтов при выходе из паузы без полного перезапуска процесса (с валидацией через `load_pipeline_config` и откатом к старому конфигу при ошибке парсинга).
- **Принудительная эскалация оператором:** `orchestrator escalate <task_id> [--to architect|hard] [--reason "..."]` (и через `control_inbox` / Telegram / UI) для перевода буксующей задачи в `arch_pending` или смены сложности без ручной правки `tasks.json`.
- **Каскадная разблокировка при перезапуске:** `orchestrator retry <task_id> [--unblock]` — одной командой сбрасывает упавшую задачу в `todo` (`attempts=0`) и переводит в `todo` все downstream-задачи, заблокированные каскадом из-за неё.
